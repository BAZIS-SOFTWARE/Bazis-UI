# AGENTS.md

## Контекст проекта

Цель проекта - это создать полнеценное GUI для проведения CAE анлиза на ядре BazisCORE. 
BazisCORE строится на CAD ядре, которе в перспективе может быть переменным.
Проект BazisGUI.Win является устаревшим, но его поддержка все еще ведется. Основное GUI сейчас BazisGUI.Avalonia

Особенности BazisCORE:

- Вспомогательные геометрические сущности и операции над ними - Geometry
- Сеточные сущности и операции над ними - Model
- Видовое представление и операции с ним в классе ModelView. Особенности построения рисования смотри в файле ModelView.md в проекте OperationalController
- Сущности граничных условий и свойства рассматриваемых сред и операции над ними - Project
- Пре и пост процессор - PreProc, PostProc
- Операционный контроллер - OperationalController, который связывает сеточные сущности и операции над ними, сущности граничных условий и свойства рассматриваемых сред и операции над ними, геометрические операции и CAD ядро (сейчас OOC через GMSH.dll)


## Правила кодирования
- Стараться не использовать глобальные переменные
- Явно не типизировать переменные, там где это не нужно

## Правила проектирования
- Придерживайся принципов SOLID и ООП.
- используй в качестве справки при решении архитектурных вопросов источник swebok-v3.pdf в папке Info
- При проектировании классов старайся не дублировать ссылки на существующие объекты.
- Не создавай методы в классах под атомарные операции не получив явного разрешения.
- Не планируй вызывать события в горячих (нагруженных) циклах - больших коллекциях, чтобы не порождать огромное кол-во однотипных сообщений

## Правила документирования
При изменении кодовой базы компонентов следует создвать диаграммы классов для проектов входящих в решение, кроме тестовых.

Если проект ссылается на другой проект и использует его структуры данных, то не следует подробно описывать структуры подключаемого проекта, а лишь разместить точку входа для этих структур (метод, перечисление и т.д.) на диаграмме.

Для интерфейсов на диаграмме необходимо показывать состав: методов, событий, свойств.

Для классов на диаграмме необходимо показывать используемые методы, события. Если класс реализует интерфейс, то дублировать информацию не требуется, а нужно только добавлять те методы, которых нет в наследуемом интерфейсе.

Не нужно строить диаграммы для исключенный из проекта файлов, где храняться классы и прочие структуры данных.

После подготовки диаграмм mdpulm нужно проверить помещается ли диаграмма в область рендера. Если нет, то ее следует разбить на несколько диаграмм. 
При подготовке диаграмм `.mdpuml` сохранять файлы с окончаниями строк CRLF для корректного отображения в Visual Studio 2022.
Каждая поддиаграмма называется также как материнская, но с приставкой в виде цифры.
Вынесенные на поддиаграммы компоненты следует помечать на материнской и указывать место их расположения (название поддиаграммы). На диаграммах должны быть ссылки друг на друга, чтобы можно было осуществлять навигацию.

В итоге для каждого проекта готовится единый многостраничный pdf, где собираются все диаграммы кроме тестовых проектов. Ссылки, используемые для навигации, на диаграммах должны поддерживаться в pdf документе и по клику открывать страницу на которой расположена искомая диаграмма.

Например: для проекта Model создается Model.mdpuml, Model-1.mdpuml, Model-2.mdpuml и т.д. Model и Model-1 расположены на разных страницах итогового pdf. На странице с Model есть указание в виде ссылки на Model-1. По клику на ссылку должен произойти переход на страницу с Model-1. Создание итогового pdf требует отдельного разрешения.

## Выбор объектов в BazisGUI.SceneCore

- `ScenePickKind` сохраняется. Способ обработки координат определяется видом объекта, а не количеством точек в `ScenePickObject`.
- Для кривой координаты задают ломаную. При выборе проверяются соседние сегменты `(0, 1)`, `(1, 2)`, `(2, 3)` и так далее.
- Для поверхности координаты задают последовательность явных треугольников: `(0, 1, 2)`, `(3, 4, 5)` и так далее. Количество точек должно быть кратно трём.
- На границе клиентских интерфейсов BazisGUI.Win и BazisGUI.Avalonia поверхности CAD и грани элементов сетки передаются в SceneCore как треугольники. Грани конечных элементов в BazisCORE выпуклые, поэтому их можно триангулировать по упорядоченным узлам.
- При выборе точкой и рамкой поверхность проверяется по отдельным треугольникам, кривая — по отдельным сегментам. При выборе рамкой порядок точек и повторяющиеся вершины треугольников должны сохраняться; `HashSet` для этой последовательности не подходит.
- При выборе рамкой для каждого сегмента кривой и каждого треугольника поверхности сначала проверять все вершины проверяемого примитива. Если они внутри рамки, считать выбранным весь исходный объект и завершать его проверку.
- Если не все вершины примитива внутри рамки, проверять пересечение его рёбер с рёбрами рамки. При обнаружении пересечения считать выбранным весь исходный объект и завершать его проверку. Если пересечения нет, переходить к следующему примитиву; отсутствие выбора фиксировать только после проверки всех примитивов исходного объекта.
- Для треугольника поверхности после проверки пересечений дополнительно проверять, лежат ли все четыре вершины рамки внутри треугольника. Если да, считать выбранной всю исходную поверхность и завершать её проверку. К следующему треугольнику переходить только при отсутствии всех трёх условий выбора.
- `Hull2DCreator` и `Polygon` из Geometry не переносить в SceneCore и не использовать для выбора поверхностей. Зависимость BazisGUI.SceneCore от Geometry должна быть устранена; преобразование данных BazisCORE выполняется на границе с Win и Avalonia.
